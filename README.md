# github.com/bazelbuild/buildtools (v1 compatibility release)

The Go module `github.com/bazelbuild/buildtools` has moved to
[`github.com/bazel-contrib/buildtools/v10`](https://pkg.go.dev/github.com/bazel-contrib/buildtools/v10).
Development continues on the
[main branch](https://github.com/bazel-contrib/buildtools) under the new path.

This branch contains the `v1.x.y` releases of the old module path. They exist
so that programs can mix packages that import the old paths with packages
that import the new ones. For example, a Gazelle extension can keep importing
`github.com/bazelbuild/buildtools/build` while Gazelle itself uses
`github.com/bazel-contrib/buildtools/v10/build`.

## How it works

Every package of the old module forwards to the package of the same name in
`github.com/bazel-contrib/buildtools/v10`:

* Every exported type is a type alias of the v10 type. `*build.File` from either
  path is therefore the same type and can be passed freely between them.
* Every exported function calls the corresponding v10 function, so there is
  only one implementation and one copy of its global state.
* Every exported constant is defined in terms of the v10 constant.
* Every exported variable is initialized from the v10 variable. Go can't alias
  variables, so **assigning to a variable of the old module has no effect**.
  Assign to the v10 variable instead (for example `build.DisableRewrites`,
  `edit.ShortenLabelsFlag`, `file.DisableSymlinkSafety`, or the variables in
  `tables`).
* Importing `github.com/bazelbuild/buildtools/edit/safe` for its side effects
  imports `github.com/bazel-contrib/buildtools/v10/edit/safe`.

The `buildifier`, `buildozer`, and `unused_deps` commands are built from the
v10 packages, so `go install github.com/bazelbuild/buildtools/buildifier@latest`
keeps working.

The forwarding packages are generated by [`internal/forwardgen`](internal/forwardgen/main.go).
